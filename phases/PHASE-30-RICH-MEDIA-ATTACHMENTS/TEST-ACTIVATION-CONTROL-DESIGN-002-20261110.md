## Deployment receipt without redeployment

An environment edit carrying the current deployment receipt would create another deployment and invalidate that receipt's identity. Deliver the independently observed receipt after deployment through the existing approved TEST database boundary instead. No HTTP control endpoint/header, independent bearer ticket, provider secret, new credential or global worker is introduced. This is a proposed diagnostic-control record and state machine, not a completed schema/API or runtime admission path.

Deploy the exact reviewed source with the literal complete manifest packaged as an immutable artifact. Source SHA and literal manifest SHA256 are external pins; neither is derived from an embedded own-hash/self-referential source field. All four rollout flags remain false. Cold identity/configuration/hash checks precede any control-record access; pending activation never initializes attachment/provider processing or grants a request.

After those checks, one finite boot may wait for a specifically addressed run/control record using bounded read-only checks against the approved TEST database and fixed tooling schema. The operator durably arms one immutable tuple: runId, activationId, exact source SHA, full manifest hash, service, deployment ID, boot correlation identity and the original notBefore/expiresAt. A boot identifier is nonsecret correlation, not authentication. It must be generated/observed for this actual process and cannot be copied to a replacement boot to resume a run. The operator must not replace a durably armed boot tuple. Missing, mismatched, expired or already-consumed records deny; waiting is bounded by the original expiry and never creates an automatic replacement run.

Only the authorized external operator observes the exact current Live deployment, full source SHA, service identity, original disabled start command/all-four-false state and matching boot correlation, then persists one immutable fresh receipt for that tuple. App-reported service/SHA or agreement between two supplied strings is not an independent observation of the deployment. Recheck current Live identity when correlation could be stale; do not authorize an older overlapping deployment with a receipt for the newer one.

The armed process consumes that matching receipt and transitions the durable run to ACTIVE in one short transaction. Database clock_timestamp checks the original validity window at the actual admission point; receipt freshness, exact tuple/boot/source/manifest equality, not-consumed status and one-use run state must all hold. Commit uncertainty grants no in-memory admission authority: retain the durable ownership/debt, inspect exact existing facts and never blindly retry activation. Request reservations remain independent durable transactions before product/domain work. No diagnostic run lock is held across product locks or provider I/O.

Restart, operator delay, deployment failure, timeout or expiry cannot renew/shift the manifest window. A manifest that expires during build/review/deployment fails closed; preparing a fresh reviewed run is separate from automatically extending this one. No provider/application fixture mutation precedes full validated manifest ownership, durable slots and actual activation. Expiry removes new-request authority but does not clear uncertain writes, burned slots or natural seven-day retained history.

Preserve sanitized external observation evidence and distinguish the external writer's procedure from application validation. No DB-owner/DDL isolation, signed upstream attestation or actual Render process-deployment-ID variable is assumed.

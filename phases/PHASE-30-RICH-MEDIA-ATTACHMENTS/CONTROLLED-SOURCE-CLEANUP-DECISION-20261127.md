# Controlled source upload and internal cleanup decision

Accepted source contract, 2026-11-27; implementation and acceptance remain pending. Phase30-002 stays IN_PROGRESS/REMEDIATE_AND_RETEST;003+ NOT_STARTED. This decision extends the controlled continuation pattern of DEC-040 and narrowly extends the prior HTTP-only allocation-coverage rule for one separately declared internal cleanup entry.

A single CREATE_SOURCE upload attempt consumes exactly five HTTP roles: UPLOAD_OWNER, SOURCE_OBJECT, SOURCE_ATTEMPT, PUT_CLAIM and PUT_SUPERVISION. Each identity belongs to the original matched policy instance and exact attachment. Completed upload replay and other producer/recovery operations require their own later reviewed contracts. No random-ID fallback is allowed on this controlled path.

An optional closed internalCleanup array permits at most one entry per eligible source object, bounded to four entries per run. Each entry names the creator operation, exact attachment/source object and its CLEANUP_JOB slot. Lowering derives immutable attempt/claim/supervision/hash/size correlation from that same validated declaration. Preparation seals exact disjoint coverage of HTTP-owned and internal-owned slots; missing, shared, duplicate or orphan slots reject the entire preparation. An internal entry has no synthetic HTTP request, request allowance or additional producer grant. Existing declarations without internal entries retain their coverage semantics. Stored SQL proof fields are procedural attestations under the shared database role; they are not independent or cryptographic proof of original-process quiescence.

Forward SQL stages reacquire original run, request-attempt and bound-operation ownership before existing domain locks on the same client, with bounded waits and fresh original expiry/cancellation checks. Native session/ACL checks remain required. Input spooling and physical PUT occur outside SQL locks. Spool size/hash must match before claim. An uncertain claim COMMIT keeps the original supervisor and exact claim without dispatch; inspection determines committed ownership before UNSENT cleanup. Claim acknowledgement alone must not be described as a current SQL run-state observation at physical dispatch. The dispatch boundary requires a fresh SQL admission gate followed by synchronous original lifetime/signal checks; neither this nor a pre-COMMIT check guarantees atomicity with later physical I/O or acknowledgement.

Cleanup is a distinct, original request-local authority. It requires the privately issued upload context, exact retained claim/supervisor/owner/version tuple, actual local input closure, and either certified never-sent supervision or actual original STARTED-to-SETTLED evidence. Copied objects, stored strings, expiry, timeout or negative HEAD alone cannot establish quiescence. An actual late positive receipt may be recorded only when input integrity and provider receipt were genuinely observed. Unknown outcomes retain debt and original settlement ownership.

After expiry/cancellation, cleanup-only work may terminalize the exact owner, record an authentic late receipt, burn the one planned internal job and settle actually quiescent ownership. It cannot promote PENDING, refund diagnostic burns, create a second cleanup job, start another PUT/worker or delete provider objects. Every reached cleanup branch must ensure the same planned active job; a completed or foreign job fails closed with retained debt. A spool failure before object creation needs no cleanup job. Byte/metadata retention debt remains until separately verified physical cleanup.

Alternatives rejected: attaching CLEANUP_JOB to a fake HTTP request corrupts request accounting; ordinary cleanup allocators mint unplanned identities; immediate lease release after uncertain PUT loses ownership; timeout or HEAD-derived quiescence can race a late write. Retaining the original supervisor and separately sealed job gives finite allocation and a verifiable recovery path.

Required verification includes actual PostgreSQL transition/coverage constraints, exact five identities at dispatch, no-provider mismatch/copy rejection, abort and lost claim acknowledgement, late settlement after expiry/tombstone, idempotent planned cleanup and failure retention. Existing ordinary upload behavior must remain covered. Production main, ordinary startup flags and workers stay unchanged. This decision grants no fixed schema installation, runtime activation, provider access or Phase30 acceptance.
